# 技術面接スクリプト - 頑張ったこと

## 1. グループチャット実装（複雑な処理フローの設計と実装）

### Situation（状況）

**グループチャット機能の概要**：

ユーザーが事前に作成したAIエージェント（例：Slack連携のエージェントA、Notion連携のエージェントB、データ分析用のエージェントC）を選んでグループを作成し、1つのチャットルームで複数エージェントと同時に対話できる機能です。各エージェントの設定（使用モデル、振る舞い、連携サービス、システムプロンプトなど）は完全に保持されます。

**機能の特徴**：

- ユーザーがメッセージを送ると、グループに参加している全エージェントをメンション
- メンション順（エージェントA → B → C）に各エージェントが順番に応答
- 各エージェントは前のエージェントの発言を参照しながら、会話の流れに沿って対話可能

この機能を実装する際、**バックエンドの処理フローが非常に複雑**になることが最大の困難でした。

### Task（課題）

**バックエンドで実装すべき複雑な処理フロー**：

1. **会話履歴の動的構築**: エージェントAが応答中、エージェントBは「ユーザーメッセージ + エージェントAの応答」を履歴として参照する必要がある。つまり、処理中に履歴が動的に増えていく
2. **リアルタイムストリーミングとDB保存の両立**: LLMからトークンが届くたびにフロントエンドに送信しながら、ストリーム完了後にDBに保存する必要がある。ツール使用情報も同様
3. **部分失敗の許容**: エージェントBがエラーになっても、エージェントCは処理を継続する必要がある。ただしエラー情報はDBに記録し、統計情報の整合性も保つ
4. **統計情報の自動更新**: メッセージ数や最終メッセージ時刻などをリアルタイムで更新し、アプリケーション側の更新忘れを防ぐ

これらの処理を、**保守性を保ちながら**実装する必要がありました。

### Action（行動）

#### **1. バックエンド処理フローの設計と実装（3フェーズ・14ステップ）**

**【フェーズ1: 初期化とユーザーメッセージ保存】**

1. グループチャット取得・権限確認
2. メンバーリスト取得
3. ユーザーメッセージをDBに即座に保存（`group_messages`）
4. メンションリスト構築（`@all`なら全メンバー展開、順序付き）
5. 全メンションをDBに保存（`message_mentions`、`status='pending'`）
6. フロントエンドに`user_message_saved`, `mention_queue`イベント送信

**【フェーズ2: 各エージェントの直列処理】**（`for`ループで1エージェントずつ）

7. メンション開始: `status='processing'`に更新、`agent_preparing`イベント送信
8. **会話履歴の動的構築**:
   - 過去メッセージを取得
   - 同一メッセージ内の**既に完了したAI応答**を`mention_order`順に追加（自分より後は見えない）
   - 最新20件に制限（トークン最適化）
9. AIエージェント情報取得（モデル、温度、トークン数、プロンプト）
10. サービス設定取得・認証情報復号化（Slack/Notion等のAPIキー）
11. **動的システムプロンプト生成**（グループ状況 + 共通プロンプト + 固有プロンプト）
12. JSONリクエスト生成 → Python AI APIへSSEストリーミング
13. **ストリーミング処理**:
    - トークンを受信しながら`agent_chunk`イベントをリアルタイム送信
    - ツール使用を検知したら`tool_start`, `tool_end`イベント送信
    - **メモリ上に一時保存**（DB保存はまだしない）
14. **ストリーム完了後にDB一括保存**:
    - AI応答メッセージ全文を`group_messages`に保存
    - トークン使用量を`chat_sessions`に保存
    - 全ツール使用を`tool_usages`に保存（`group_message_id`で紐付け）
    - メンション: `status='completed'`, `response_message_id`設定
    - `agent_complete`イベント送信 → **次のエージェントへ**

**【フェーズ3: 全完了】**

- 全メンション処理完了後、`all_complete`イベント送信
- ユーザーメッセージ: `processing_status='completed'`に更新

#### **2. 4つの工夫点**

**① DB保存タイミングの最適化**

- ストリーミング中はメモリ内で蓄積、完了後に一括保存 → DB負荷軽減、レイテンシ最小化

**② エラー時のスキップ処理（Graceful Degradation）**

- 1エージェントが失敗しても`continue`で次へ進む
- エラーメッセージをログ出力、メンションステータスを`failed`に更新してDB記録
- Contextキャンセル時は未処理メンションを一括で`cancelled`に更新

**③ 統計情報の整合性保証（PostgreSQLトリガー）**

- トリガー`update_group_chat_on_message()`が`group_messages`のINSERT/DELETEを監視
- `group_chats.message_count`, `last_message_at`を自動更新
- アプリケーション側の更新忘れを防止

**④ PostgreSQLインデックスによるクエリ最適化**

- **複合インデックス**: `idx_group_messages_group(group_chat_id, created_at DESC)` → 会話履歴取得クエリを高速化
- **部分インデックス**: `idx_group_chats_active(user_id, is_active) WHERE is_active = true` → アクティブなグループのみをインデックス化、インデックスサイズ削減
- **メンション処理用インデックス**: `idx_mentions_message(message_id, mention_order)` → メンション順序での取得を高速化
- **処理中ステータス用部分インデックス**: `idx_mentions_status(status) WHERE status IN ('pending', 'processing')` → 処理中メンションの検索を最適化

**⑤ アーキテクチャによる保守性向上**

- **GoとPythonの責任分離**: Go側でビジネスロジック（直列処理、DB保存制御、エラーハンドリング）、Python側でLLM推論
- **Clean Architecture + DDD**: Usecase層でビジネスロジック集約、Domain層で状態管理、Infrastructure層でDB操作分離 → 変更の影響範囲を限定

### Result（結果）

- **複雑な処理フローの実装成功**: 動的な履歴構築、ストリーミングとDB保存の両立、部分失敗許容、統計情報自動更新を実現
- **会話の流れの維持**: 各エージェントが前のエージェントの発言を参照しながら、自然な会話の流れを実現
- **パフォーマンス向上**: DB保存タイミング最適化によりストリーミングレイテンシを最小化。複合インデックスにより会話履歴取得クエリを高速化
- **保守性とデバッグ性**: アーキテクチャの分離により各層の責任が明確。エラー時のステータス管理により、どのエージェントで失敗したかを追跡可能

## 2. APIキー暗号化（ユーザー体験・セキュリティ・データ整合性のバランス設計）

### Situation（状況）

ユーザーが外部サービス（Slack、Notion等）のAPIキーを登録する際、**3つの要求を同時に満たす**必要がありました：

1. **セキュリティ**: APIキーを安全に保存し、改ざんを検知
2. **ユーザー体験**: 無効なキーを保存してしまい、後でエラーになる事態を防ぐ
3. **データ整合性**: 暗号化データが破損していないことを保証

### Task（課題）

**3つの技術的課題**：

1. **単純な暗号化だけでは不十分**: AESだけでは改ざん検知ができず、復号化時にゴミデータが返る可能性
2. **保存前にキーの有効性を確認する必要**: 無効なキーを暗号化してDB保存してしまうと、ユーザーがチャット時に初めてエラーに気づく（UX低下）
3. **リプレイ攻撃のリスク**: 同じNonceを再利用すると、攻撃者が過去の暗号文を再送できる

これらを**保守性を保ちながら**実装する必要がありました。

### Action（行動）

#### **1. 暗号化処理フローの設計（3ステップ）**

**【ステップ1: Python APIでキー検証】**

- ユーザーからAPIキーを受信
- **Go側からPython APIに検証リクエスト**を送信
- Python側で実際のサービスAPI（Slack/Notion等）を呼び出し、キーの有効性を確認
- 無効なキーの場合は**即座にエラーを返す**（Fail Fast原則）

**【ステップ2: Go側でAES-256-GCM暗号化】**

- 検証が成功したキーのみを暗号化処理へ
- **Nonceの生成**: `crypto/rand`で96ビット（12バイト）のランダムNonceを生成
- **AES-256-GCM（AEAD）で暗号化**: 暗号化と認証を1ステップで実行、128ビットの認証タグを自動付与
- 暗号文とNonceをそれぞれDBに保存

**【ステップ3: DB保存と復号化】**

- 暗号文、Nonce、認証タグをPostgreSQLに保存
- 復号化時、GCMが自動的に認証タグを検証 → 改ざんがあれば復号化失敗

#### **2. 3つの工夫点**

**① AES-256-GCM（AEAD）による改ざん検知**

- **共通鍵暗号方式を選定した理由**:
  - **パフォーマンス**: 公開鍵暗号（RSA等）より数百倍高速。チャット時に毎回復号化するため、レイテンシが重要
  - **用途の適合**: サーバー内での暗号化・復号化のみ。クライアント間の鍵共有は不要
  - **管理のシンプルさ**: 1つのマスターキーをAWS Secrets Managerで一元管理
- **認証付き暗号化（AEAD）**: 暗号化と認証を1ステップで実行
- **128ビット認証タグ**: 暗号文に自動付与され、改ざんを検知
- **復号化時の自動検証**: `gcm.Open()`が認証タグを検証し、改ざんがあれば復号化失敗
- **メリット**: データ整合性を保証、ゴミデータの返却を防止

**② 保存前検証（Fail Fast原則）によるUX向上**

- **検証フロー**: Go → Python → 外部サービスAPI（Slack/Notion等）
- **無効キーの早期検知**: DB保存前にエラーを返すため、ユーザーは登録時に気づける
- **エラーメッセージ**: サービスごとの具体的なエラー理由を返却（例: 「Slackトークンの権限が不足しています」）
- **メリット**: ユーザーがチャット時に初めてエラーに気づく事態を防止

**③ Nonce管理とマスターキー管理**

- **Nonceの完全ランダム化**: 各暗号化ごとに`crypto/rand.Reader`で96ビットのNonceを生成
- **リプレイ攻撃の防止**: 同じNonceが再利用されることを防ぐ
- **マスターキー管理**: AWS Secrets Managerで256ビット（32バイト）のマスターキーを管理、環境変数への直接保存を回避
- **メリット**: セキュリティリスクを最小化

### Result（結果）

- **セキュリティの確保**: AES-256-GCMによる認証付き暗号化で改ざん検知、AWS Secrets Managerでマスターキー管理
- **UXの向上**: 保存前検証により無効キーの早期検知、ユーザーは登録時にエラーに気づける
- **データ整合性の保証**: 認証タグによる自動検証で、破損データの復号化を防止
- **保守性**: Go側で暗号化ロジック、Python側で検証ロジックと責任分離。暗号化アルゴリズムの変更時も影響範囲が限定的
