## スライド3｜そもそもLLMとは？

**スライドに載せる要点**
- LLM = 大規模言語モデル（ChatGPT / Claude など）
- 実行には**膨大なGPUリソース**が必要
- だから普通は**クラウド上**で動き、APIでアクセスする

**話す原稿**
> LLM、大規模言語モデルは、ChatGPTやClaudeでおなじみの「対話型AI」の中身です。
> これらが基本クラウドで動いているのには理由があって、**動かすのに大量のGPUが要る**からです。手元のスマホやノートPCで気軽に動かすのは難しい。だからサーバー側で動かして、私たちはAPI経由で使う、というのが標準の形でした。

## スライド4｜潮流：クラウドからローカルへ

**スライドに載せる要点**
- プライバシー／個人情報保護の重要性が上昇
- iOS / Android も**OSレベルでLLM機能**を提供開始
- ローカル実行のうれしさ：
  - オフラインでも使える
  - 機密データを**外部に送らない**

**話す原稿**
> ところが最近は流れが変わってきています。プライバシーへの意識が高まって、「データを外に出さずに、手元でAIを動かしたい」というニーズが増えてきた。実際にiOSやAndroidもOSの機能としてLLMを載せ始めています。
> ローカルで動けば、ネットがなくても使えるし、入力した内容がサーバーに送られないので、機密情報も安心して扱える。この「ローカルで動くLLM」を、ブラウザだけで実現するのが今日の主役 **WebLLM** です。

## スライド5｜WebLLMとは

**スライドに載せる要点**
- **ブラウザ上でLLMを動かす** JavaScriptライブラリ（`@mlc-ai/web-llm`）
- 実行時に必要なモデルを**ダウンロードして利用**
- サーバー不要・ページに組み込むだけ

**話す原稿**
> WebLLMは、ウェブブラウザの中でLLMを動かすためのJavaScriptライブラリです。あらかじめ用意された複数のモデルから選んで、初回にダウンロードして使います。
> ポイントは「サーバーが要らない」こと。ウェブページにスクリプトを読み込むだけで、その人のブラウザの中で完結してAIが動きます。

---

## スライド6｜WebLLMを支える技術

**スライドに載せる要点**
- **WebGPU**：ブラウザからGPUに直接アクセス → 高速計算
- **WebAssembly (Wasm)**：C/C++級の処理をブラウザで高速実行
- **キャッシュストレージ**：一度DLしたモデルは保存、次回から高速

**話す原稿**
> 仕組みを支えているのは主に3つ。まず **WebGPU**、これはブラウザからGPUを直接叩ける新しいAPIで、これが計算の速さの肝です。次に **WebAssembly**、重い処理をブラウザ上で高速に動かす技術。そして **キャッシュ**。モデルは一度ダウンロードするとブラウザに保存されるので、2回目以降はすぐ起動します。
> 注意点として、モデルは数百MB〜数GBと大きいので、ストレージをそれなりに食います。ここは後で実装の落とし穴にもつながります。

## スライド7｜メリット・デメリット

**スライドに載せる要点**
- メリット
  - プライバシー：入力がサーバーに出ない
  - オフライン可・**追加コスト$0**（サーバー費用ゼロ）
  - 導入が容易（ページに組み込むだけ）
- デメリット
  - **速度**：クラウドより遅い（端末GPU依存）
  - **品質**：小型モデルは賢さ控えめ・**ハルシネーション**
  - 初回に**大きなDL**・ストレージ消費・**Safari非対応**

**話す原稿**
> メリットとデメリットを整理します。メリットは、プライバシー、オフライン、そして何より**サーバー費用がかからない**こと。個人開発だとここが効きます。
> 一方デメリットは、クラウドより遅いこと、小型モデルだと賢さが足りずウソ（ハルシネーション）を出しやすいこと、初回のダウンロードが大きいこと。あとSafariはWebGPU未対応、という現実的な制約もあります。

## スライド8｜最小コード：モデルの読み込みと生成

**スライドに載せる要点**
- `CreateMLCEngine(modelId, {...}, appConfig)` でロード
- `engine.chat.completions.create(...)` で生成（OpenAI互換API）

```js
const engine = await webllm.CreateMLCEngine(selectedModel, {
  initProgressCallback: (p) => console.log(p), // DL進捗
});

const reply = await engine.chat.completions.create({
  messages: [
    { role: "system", content: "You are a helpful AI assistant." },
    { role: "user", content: "Monacaについて教えて" },
  ],
});
```

**話す原稿**
> コードもすごくシンプルです。`CreateMLCEngine` でモデルをロードして、あとは `chat.completions.create` を呼ぶだけ。見ての通り **OpenAIのAPIとほぼ同じ形**なんです。だから既存のコードからの移行がしやすい。
> `initProgressCallback` でダウンロードの進捗を受け取れるので、プログレスバーも出せます。

## スライド9｜小型モデルの限界（正直な話）

**スライドに載せる要点**
- 記事の実例：「Monacaについて教えて」への回答
- 同じ項目を繰り返す・事実誤り（ハルシネーション）
- パラメータが小さいほどリスク大

**話す原稿**
> ただし、正直な限界も見せておきます。参考記事では小型モデルに「Monacaについて教えて」と聞いた例が載っていて、回答が「無料です」を何度も繰り返したり、事実と違うことを言ったりしています。
> これは小型モデルの典型的な弱点で、**同じ言葉を繰り返すループ**や**ハルシネーション**が起きやすい。実は私も後でこれに正面からぶつかりました。ここは覚えておいてください。

## スライド10｜ここからが本題：NeuraKnotに組み込む

**スライドに載せる要点**
- NeuraKnot = AIと人間の境界を消すチャットアプリ
- 既存構成：フロント(Next.js) → Go API → Python → クラウドLLM

**話す原稿**
> ここからが本題です。私が作っている NeuraKnot は、AIと人とチャットできるアプリで、これまでは「フロント → Go → Python → クラウドのLLM」という**完全サーバー推論**の構成でした。
> ここに「無料・プライベートに使えるローカルLLM」を選択肢として足したい、というのが今回のモチベーションです。

## スライド11｜設計の壁：アーキテクチャが「サーバー前提」

**スライドに載せる要点**
- 既存は全部サーバーで推論する前提
- ローカルLLMは**ブラウザで推論**＝経路がまったく違う
- でも会話履歴・課金・分析は**サーバーDBに残したい**

**話す原稿**
> 最初にぶつかった壁は、既存アーキテクチャが「推論はサーバーでやるもの」という前提で全部組まれていたことです。ローカルLLMは推論がブラウザで起きるので、根っこの流れが違う。
> かといって、会話の保存や分析まで全部クライアントに移すのは避けたい。**「推論だけローカル、保存はこれまで通りサーバー」**を両立する設計が必要でした。

---

## スライド12｜キーアイデア：実行場所で分岐する

**スライドに載せる要点**
- LLMごとに `execution_location` を持たせる
  - `server`：openai / anthropic / google（従来どおりPython推論）
  - `client`：**webllm（ブラウザ推論）**
- WebLLMを「第4のプロバイダー」として**他LLMと同じ管理画面で追加**

**話す原稿**
> 解決のキーアイデアはシンプルで、モデル定義に「**実行場所（execution_location）**」という属性を1つ足しました。`server` なら今まで通りサーバーで、`client` ならブラウザで推論する。
> これで WebLLM を「OpenAIやClaudeと並ぶ4つ目のプロバイダー」として、管理画面から**まったく同じ操作で追加**できるようになりました。特別扱いしない、というのがミソです。

## スライド13｜処理フロー：prepare → ブラウザ推論 → complete

**スライドに載せる要点**

```
[client-runtime (webllm)]
ブラウザ → Go : メッセージ送信
Go        : 実行場所を判定・ユーザー発言を保存・"材料"を組立
Go → ブラウザ : {system_prompt, 履歴, model, params}  ← 推論しない
ブラウザ   : WebLLMで推論（ストリーミング表示）
ブラウザ → Go : 生成結果を送信（complete）
Go        : AI発言を保存＋使用量を$0で記録
```

**話す原稿**
> 具体的な流れです。ブラウザがメッセージを送ると、Goサーバーは**推論せず**に「システムプロンプト＋会話履歴＋パラメータ」という“材料”だけを返します。
> ブラウザはそれを受け取ってWebLLMで生成し、画面にストリーミング表示。生成が終わったら結果をサーバーに送り返して、AIの発言として保存します。このとき**課金は$0**で記録します。
> ポイントは、**クライアント推論のときはPythonを一切通らない**こと。ここがサーバーコスト削減の実装上の要です。

## スライド15｜ハマり①：Dockerの匿名ボリューム

**スライドに載せる要点**
- 症状：`Module not found: '@mlc-ai/web-llm'`（package.jsonには有るのに）
- 原因：コンテナの `/app/node_modules` が**匿名ボリューム**で、依存追加前の状態のまま
- 対処：コンテナ内で `npm install` して同期

**話す原稿**
> ここから「教科書に載ってない」実践編です。
> まず、ライブラリを追加したのにビルドが「モジュールが見つからない」と怒る。原因はDockerで、`node_modules` がコンテナ専用の匿名ボリュームになっていて、**ライブラリを足す前の古い中身のまま**だったからです。コンテナの中で `npm install` し直したら解決。環境まわりの定番の罠でした。

## スライド16｜ハマり②：コンテキストウィンドウ超過

**スライドに載せる要点**
- 症状：`Prompt tokens exceed context window size (4112 > 4096)`
- 原因：小型モデルの文脈枠は小さい。履歴20件だと入力だけで溢れる
- 対処：**履歴を自動トリミング＋超過時に半減リトライ**（生成前に検知できるので二重描画なし）

**話す原稿**
> 次。会話が少し長くなると「入力が文脈の枠を超えた」というエラー。クラウドの大きなモデルなら余裕ですが、ローカルの小型モデルは枠が4096トークンと小さく、履歴を積むと入力だけで溢れます。
> 対処は、履歴を最新側から入る分だけに切り詰めて、それでも溢れたら件数を半分ずつ減らして再試行する方式。超過は生成が始まる前に分かるので、画面に文字が二重に出る心配もありません。

## スライド17｜ハマり③：小型モデルの反復ループ

**スライドに載せる要点**
- 症状：「と、と、と、と…」と同じ語を無限に繰り返す（＝スライド9の現象）
- 原因：小型モデルは degeneration（縮退）を起こしやすい
- 対処：`frequency_penalty` / `presence_penalty` / `repetition_penalty` を付与、温度を安全域に

**話す原稿**
> そして3つ目、まさにスライド9で予告した現象です。「と、と、と…」と同じ文字を延々繰り返す。小型モデルにありがちな“縮退”です。
> これは反復ペナルティ系のパラメータを効かせ、温度（temperature）も低すぎ・高すぎを避けて安全な範囲に収めることで大きく改善しました。クラウドの大型モデルでは要らない調整が、ローカルでは必要になる、という良い学びでした。

## スライド18｜モデル選定：どれを使うべきか

**スライドに載せる要点**
- 迷ったら **Llama-3.2-3B**（品質×軽さの総合バランス最良）
- 軽量×日本語なら **gemma-2-2b-jpn-it**
- GPUがあり品質重視なら **Llama-3.1-8B** / 日本語最高峰は **gemma-2-9b**
- 最軽量の動作確認は **Llama-3.2-1B / gemma3-1b**
- 70Bは最強だが**ブラウザでは実質動かない**

**話す原稿**
> 「結局どれを使うの？」への答えです。総合バランスなら3Bの Llama-3.2-3B が現実的な最適解。日本語を軽く動かすなら日本語チューニング済みの gemma-2-2b-jpn。GPUに余裕があれば8Bや9Bで一気に賢くなります。
> 逆に70Bクラスは品質は最強でも、必要メモリが大きすぎてブラウザでは動きません。**「性能」と「動かせるか」は別の軸**として考える必要があります。

## スライド19｜補助機能の使い分け（コスパ設計）

**スライドに載せる要点**
- 質問候補生成：ローカルが使えれば**ローカルで$0**、ダメならクラウドへ自動フォールバック
- どちらで生成したかを**バッジで可視化**（ローカル / クラウド）

**話す原稿**

> 一方「プロンプトの自動強化」は、品質が重要なので**あえてクラウド固定**にしています。全部ローカルにするのではなく、**機能ごとに賢く使い分ける**のが実用上のコツです。

## スライド20｜まとめ

**スライドに載せる要点**
- WebLLMで**ブラウザだけでAI**が動く：プライバシー・オフライン・$0
- 既存アプリには「**実行場所で分岐**」して無理なく統合できる
- 小型モデルの現実（速度・品質・文脈枠・反復）には**設計と割り切り**で対応
- ハイブリッド（クラウド↔ローカル）の**使い分け**が鍵

**話す原稿**
> まとめます。WebLLMを使えば、サーバーなしでブラウザだけでAIが動き、プライバシー・オフライン・コストゼロという大きな利点が得られます。
> 既存アプリにも「実行場所で分岐する」という一手で、無理なく組み込めました。ただし小型モデルには速度・品質・文脈枠・反復といった現実的な制約があり、そこは設計と割り切りでカバーする。
> 結論として、**クラウドとローカルを目的に応じて使い分けるハイブリッド**が、今いちばん現実的で強い、というのが今回の学びです。ご清聴ありがとうございました。

## 付録｜想定質問と回答（Q&A対策）

- **Q. どのくらい遅い？**
  A. 端末GPU次第。1〜3B級なら体感で使えるが、8B以上は非力なGPUだと重い。速度重視ならクラウド。
- **Q. スマホでも動く？**
  A. iOS SafariはWebGPU非対応で不可。対応ブラウザでも1〜3B級が現実的。基本はPC想定。
- **Q. セキュリティは本当に安全？**
  A. 推論はブラウザ内で完結し入力は外部送信されない。ただし会話の保存はサーバーDBに残す設計（保存は従来同様に保護）。
- **Q. コストが$0なのは本当？**
  A. 推論はユーザー端末で行うためLLM API課金は発生しない。サーバーは保存と配信のみ。使用量は$0で記録。
- **Q. モデルの追加は大変？**
  A. 管理画面から他のLLMと同じ手順で追加可能。プロバイダーに「webllm」を選び、モデルIDを一覧から選ぶだけ。
